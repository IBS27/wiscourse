wiscourse — project overview

Last updated: 2026-08-17

What this is

A replacement UI for Canvas at UW–Madison. The official Canvas UI is slow and unreliable. wiscourse syncs Canvas data into its own database in the background, so every screen loads instantly and updates live. It adds better course management, a real calendar, and task management on top.

Core idea

The UI never waits on Canvas. Background jobs pull Canvas data into Convex. The UI reads only from Convex. This one decision is what makes the app fast.

Product design (decided 2026-08-17)

Shape: an agenda-first planner that mirrors Canvas. Designed generic for many students, built for one user now. Responsive PWA: sidebar on desktop, bottom tabs on mobile; light + dark; calm, dense, keyboard-friendly.

Unified todos. One todos concept. Canvas assignments (incl. graded discussions and quizzes) are non-deletable todos; personal tasks are local only — no Canvas Planner round-trip. Each todo has a planned date, embedded subtasks, and notes. Done = manual or auto on submission; un-done is allowed. Quick-add parses natural language ("read ch 4 fri #cs537"). Todos and notes are kept forever.

Agenda rules. A todo shows on its planned day, and on its due day only if not done. A missed planned date rolls to today unless the Canvas due date has passed — then it is Overdue.

⌘KSearch courses, assignments, pages, files, announcements + quick actions.

Files: client never holds the token. Prefer Canvas per-file verifier URLs fetched fresh by an action; fall back to a Convex HTTP proxy if CORS blocks preview.

Sync: active courses = active enrollments in the current or open-ended term; only those sync (past courses show from existing data). Tripwire every 2 min while the user is active (5-min client heartbeat), else 15 min; delta on trip; full nightly. Manual refresh + "last synced" everywhere.

Writes in v1: todos (optimistic) and assignment submission (file / text / URL through a confirmed outbox, last milestone). Everything else links out.

Deferred: discussions, Canvas Inbox messages, quiz taking, push notifications (plumbing only), Sentry, ICS import, Planner sync.

  3. Later (Phase 3): swap in the OAuth2 flow behind getCanvasClient(). Nothing above that seam changes.
Hard rules: UW students cannot self-generate tokens (disabled Nov 2025). Asking another user to paste a token violates the Canvas API policy. Multi-user deployment REQUIRES OAuth2 + a developer key. Do not onboard a second user before then.

Canvas API rules (verified Aug 2026)

  • REST-first. GraphQL has no calendar or planner endpoints; treat it as an optional read optimization only.
  • Throttling is on concurrency, not frequency (~12 in-flight per token). The client is strictly sequential. Treat both 403 ("Rate Limit Exceeded" in body) and 429 as throttle signals.
  • Polling only — webhooks need institution setup. Cheap pattern: poll activity_stream/summary as a tripwire; real delta sync via submitted_since / graded_since; full sync nightly.
  • context_codes[] is silently capped at 10 — always chunk.
  • Never show a score unless posted_at is set (teacher may withhold grades).
  • Assignment submission must be a confirmed write (pending/failed states), never optimistic. Optimistic updates are fine for tasks and other low-stakes writes.

Backend design (the part to keep)

  • convex/credentials.ts — the seam. getCanvasClient(ctx, userId) is the only way to reach Canvas. Tokens AES-GCM encrypted (CANVAS_ENCRYPTION_KEY env var), never sent to clients.
  • convex/sync.ts — crons dispatch → Workpool fans out one retried job per user (never loop users inside a cron; overlapping cron runs are skipped).
  • convex/canvas/client.ts — sequential fetch, Link-header pagination, rate-limit telemetry.
  • Watch Convex function-call count — it is the real scaling cost (~115 users on free tier at naive 5-min polling; the tripwire design cuts this sharply).
